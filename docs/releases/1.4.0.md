# Folder Locker 1.4.0

Folder Locker can preserve an existing workspace and reserve one additional,
disjoint protected root. Each root has an independent identity and recovery journal;
operations select one root at a time and retain the original default.

- The bounded upgrade preserves the primary configuration, journal, identities,
  permissions and flags, with a private baseline and pre-provisioning rollback.
- The additional root starts PENDING. Separate owner provisioning and explicit
  `activate-root` bind its identity; activation does not create or lock it.
- `roots [--json]` distinguishes ACTIVE registrations from PENDING reservations.
- Default `status` preserves stdout and the original selection. With an additional
  registration, stderr names the limited scope and points to `status --all`.
- `status --all [--json]` reports each registration and inspects ACTIVE roots.
  PENDING/inspection failures are UNVERIFIED and return exit 1. JSON adds
  `registration` and `default` only for the explicit global mode.
- Legacy explicit-path status and the single-root text/JSON contract are preserved.
  Consumers merging stdout/stderr should select an explicit scope or separate streams.

Read [status contracts](../status.md) and the
[two-root upgrade procedure](../two-root-upgrade.md) before adoption.

The reservation installer is deliberately limited to the reviewed 1.3.0 executable
(hash pinned in `install_two_roots.py`) and an absent second root. It is not a
registration manager for arbitrary roots. Fresh single-root 1.4.0 installations do
not yet have an add-root path; do not downgrade or edit settings to bypass this
limit. Existing active two-root installations can take ordinary binary upgrades
using the original configured root, without repeating reservation or activation.

No service, third-root support, shared-parent scope, journal migration, broad unlock
or automatic workspace creation is added. Existing symlink, mount, hard-link,
write-ahead recovery and pre-existing-flag safeguards remain.
